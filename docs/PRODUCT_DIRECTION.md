# law-tech.dev 产品方向与长期路线

更新时间：2026-06-29
状态：当前产品决策的主文档

## 一、产品定义

law-tech.dev 不以“功能很多的个人网站”为目标。它是一套私人认知工作台，同时保留一座有选择地对外开放的花园。法学、编程、日常生活和对陌生领域的好奇共享同一个底层：问题、材料、念头、行动及它们之间的关系。

公开站点负责专题、文章、课程笔记、项目和少量工具。私人工作台负责日程、课程、阅读、写作、提醒、回顾和长期记忆。公开层是出口，不是整个系统的主体。

## 二、三个长期判断标准

后续功能不使用口号式包装，但必须通过以下三个问题判断价值：

### 1. 思考的痕迹

系统不仅保存内容，还应保存为什么在意、怎样理解、后来在哪里使用，以及观点是否发生变化。普通知识库回答“有什么”，属于用户的系统还要回答“它为什么与我有关”。

### 2. 存在的证明

系统从日程、任务、课程、阅读、写作和补充记录中形成记忆锚点。目标不是连续打卡、效率排名或生产力羞耻，而是让用户能够回看某段时间真正经历、学习和思考过什么。

### 3. 探索的可能

法学是重要世界，但不能成为系统边界。系统应持续为技术、历史、设计、科学、社会问题及纯粹好奇留出入口，并帮助它们与既有课程、文章和问题建立联系。

## 三、产品气质

- 温暖、聪明，带一点冷幽默；
- 提醒但不训诫，整理但不替用户作最终判断；
- 不以 KPI、连续打卡或强制拆任务管理生活；
- 重要状态清楚，普通操作安静；
- 前端通过内容、状态和动作自证用途，不用长篇说明自身架构；
- 数据属于用户，能够导出、备份并迁移。

## 四、当前优先顺序

### 第一主工程：课程回放自动化

课程可能在上课两天后才上传；用户又可能因实习无法到场。课程系统必须主动发现新回放，完成授权获取、下载或流式读取、云端转写、课程简报、完整笔记、归档与消息推送，避免期末才面对一批从未见过的课程。

第一主工程的详细约束见 `docs/COURSE_REPLAY_AUTOMATION.md`。

### 第二主工程：Today 记忆锚点

Today 白天回答需要留意什么，晚上根据日程、完成事项、阅读、课程和写作痕迹生成当天草稿。用户通过网页、邮件或微信回复补充后，保存为轻量生活记录。它不是日记打卡器，而是“今天确实发生过”的锚点。

### 第三主工程：探索项目

用户给出一个想了解的主题后，系统帮助形成问题、检索任务和可复用提示词。高能力模型或人工研究结果可以再导回系统，由站内工具完成来源整理、概念关系、争议、现有知识连接和后续方向。界面应自然，避免把好奇心做成僵硬项目管理。

### 后续生长：统一收件与再次出现

统一入口接收链接、摘录、截图、任务、日程和念头。系统建议类型及关系，但保留人工确认。值得留下的内容应在合适的时候重新出现，避免阅读箱和收藏夹再次成为停尸房。

### 维持而不激进扩张：Writing Studio

Writing Studio 保持可靠的 Markdown 编辑、预览、导入、发布和摘要能力。问题工作区、段落证据关系、复杂版本与深度风格学习保留为未来方向，不在当前阶段抢占课程、Today 和探索系统的资源。

## 五、闭环而不是纸面阶段

路线不得使用“先搭壳、以后补齐”的方式。每一个里程碑必须形成独立可用的完整闭环，并明确验收条件。后续即使暂停，已经交付的里程碑也应继续产生真实价值。

- 课程工程的第一个闭环不是一个空页面，而是一节真实回放从授权导入到简报、笔记和消息送达；
- Today 的第一个闭环不是一张统计卡，而是当天痕迹生成草稿、用户补充并保存；
- 探索的第一个闭环不是知识图谱动画，而是一个主题生成研究任务、导入结果并形成可继续阅读的结构化页面。

“代码存在”不等于完成。完成状态继续区分：代码完成、测试通过、构建通过、Preview 验证、真实持续使用。

## 六、公开首页方向

公开首页以专题合集为主体、最近更新为侧重信息、搜索和工具为快捷入口。个人履历和口号不占据主视觉。

当前方向：

- 顶栏左侧显示本地日期时间和一条可编辑站内语料；
- 中间保留内容、工具、搜索；
- 主卡展示当前重点内容并使用真实封面；
- 普通内容卡同样展示真实缩略封面，无封面时使用稳定生成图；
- 专题栏目独立成区，不再塞进工具框；
- 常用工具由数据配置并支持横向扩展，不能固定死为四宫格；
- “正在探索”未来应由可编辑数据源驱动，不能成为长期不更新的装饰品；
- 动效只用于轻微流动和反馈，尊重减少动态效果设置，不做无法停下的跑马灯。

首版日期语料与快捷入口位于 `lib/domain/publicHome.js`。它是可维护数据源，后续可迁入私人设置页，不应散落在组件中。

## 七、消息与主动服务

微信是课程简报、Today 回顾和紧急提醒的首选目标；邮件是可靠备份与现有可用通道。二者必须使用同一消息模型，记录主题、时间、来源、状态和对应对象，避免不同渠道各自形成无法管理的孤岛。

主动消息应提供一个清楚动作或链接，而不是把长篇内容一股脑扔进聊天框。回复应关联到原对象：课程简报回复成为该课次补充，Today 回复进入当天记录。

### 2026-06-30 渠道决策

课程简报和日程主动消息直接使用微信，不再采用“先邮件、后微信”的过渡方案。站内仍是内容事实来源；微信只发送短消息和明确入口。发送链路通过 OpenClaw WeChat 插件完成，消息正文由 Law-Tech 确定，Relay 不把通知交给 Agent 改写。旧邮件代码仅保留兼容和迁移用途，不在当前设置页继续暴露。
## 八、知识关系的建设方式

先记录真实关系，再做图谱。核心对象包括问题、概念、材料、摘录、课程、草稿、项目与行动。关系包括回答、支持、反对、启发、引用、已用于和仍待解决。

第一批界面只需要显示“与此相关”“可能回答的问题”“不同观点”“已用于”和“从这里继续”。数据足够丰富后，再提供局部图谱，避免一开始制造一团漂亮但无用的毛线。

## 九、暂不优先

- 完整案件工作台；
- 实时多人协同编辑；
- 自制密码管理器；
- 大规模保存原始课程视频；
- 强制复习计划和模拟考场；
- 任务耗时统计与拖延干预；
- 多模型竞技场；
- 百分百还原 Word 排版；
- 全宇宙知识图谱；
- 激进扩张 Writing Studio。

这些方向只有在出现真实、持续使用场景时才重新进入排序。
