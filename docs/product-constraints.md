# 产品约束：公开层、工作台与今日页

记录时间：2026-06-24

## 1. 前端文案底线

前端是给用户使用的产品，不是开发草稿纸。

禁止在页面中出现：

- 架构解释词直接外露：Capture、Objects、Workflows、Publish 等。
- 像思考链或注释一样的说明句。
- “这个页面不是……它是……”这类对话式解释。
- 为了说明系统设计而写给开发者看的文字。

允许出现：

- 简短、自然、面向使用的标题。
- 能帮助用户完成操作的按钮、标签、状态。
- 私人工作台中必要但克制的操作提示。

## 2. 公开层信息架构

公开层不再设置“项目”作为一级栏目。

公开导航应收敛为：

- 内容：笔记、博客、课程笔记、读书记录、公开分享。
- 工具：可以公开访问的 OCR、引注等工具入口。
- 关于：个人简介和站点说明。
- 工作台：私人入口。

“项目”不作为单独一级栏目。能公开展示的实践可以进入“内容”或“工具”；只能本人使用的流程进入“工作台”。

## 3. 工作台定位

工作台是私人操作空间，不是公开展示页。

它负责：

- 调整内容的公开/私密/密码/有效期。
- 收集事项、微信/快捷指令输入、文件和链接。
- 管理每日安排。
- 处理课程材料和笔记生成。
- 管理阅读、写作、发布流程。
- 配置模型、通知、微信入口、快捷指令入口。

工作台里的功能不能只是模块加总，需要围绕“每天怎么用”组织。

## 4. 工作台导航约束

当前“收集箱 / 进行中 / 资料库 / 课程”等名称容易造成理解负担，需要改成更直观的分组。

推荐一级组织：

- 今日：当天安排和待处理事项。
- 随手记：来自网页、iPhone 快捷指令、微信/企业微信、手动输入的原始信息。
- 事项：已整理出的任务、提醒和日程。
- 材料：文件、链接、图片、PPT、SRT、PDF、微信文章等。
- 课程：课程材料到笔记的专门流程。
- 写作：文章、论文、读书笔记、引用材料。
- 发布：内容公开、私密、密码、有效期设置。
- 设置：模型、通知、接口、权限。

其中“材料”和“课程”的关系：

- 材料是通用对象库。
- 课程是基于材料的专门工作流。
- 页面上要表达为“课程使用材料”，不能像两个孤岛。

## 5. 今日页目标

今日页必须实际可用。

用户可以输入自然语言，例如：

> 今天要整理完商法的笔记、学工有一个 PPT 要做、有几篇微信的文章要读、晚上 7 点记得和师兄吃饭

系统应整理为若干轻盈卡片，例如：

- 学习：整理商法笔记。
- 学工：做 PPT。
- 阅读：微信文章列表，带链接。
- 日常：晚上 7 点和师兄吃饭。

每张卡片需要支持灵活字段：

- 标题
- 类型/模块
- 时间
- 地点
- 重要程度
- 完成状态
- 链接
- 子内容
- 备注

卡片排序应能根据：

- 时间
- 重要程度
- 事项类型
- 是否临近

不同类型需要有轻微视觉区分，但整体保持轻盈，不能变成厚重后台面板。

## 6. AI 接入方式

今日页和事项整理应采用 AI-ready 的 JSON 结构。

前端先围绕结构化结果设计，不绑定某个模型。

不同功能的模型配置必须分开：

- 日程/事项：使用日程模型配置。
- 课程整理：使用课程模型配置。
- 写作/阅读：后续使用写作或阅读模型配置。

不能用一个全局模型配置强行覆盖所有场景。

工作台的“设置”页负责管理这些配置，但每个功能调用自己的配置命名空间。

解析结果建议结构：

```json
{
  "items": [
    {
      "id": "string",
      "title": "string",
      "kind": "study | work | reading | life | writing | admin | other",
      "time": "string",
      "place": "string",
      "priority": "low | normal | high",
      "done": false,
      "links": [{ "title": "string", "url": "string" }],
      "children": [{ "title": "string", "done": false }],
      "note": "string"
    }
  ]
}
```

后续接 AI API 时，应只替换解析层，不能重写今日页 UI。

## 8. 日程数据存储

日程、事项、提醒最终必须保存在云端。

目标：

- 任意终端都能查看、修改。
- iPhone 快捷指令、微信/企业微信、网页输入进入同一份数据。
- 浏览器本地存储只能作为预览期和离线兜底，不能作为正式数据源。

发布后，日程模块应使用 Supabase 保存：

- 事项本体
- 解析来源
- 编辑记录
- 提醒时间
- 链接和子项
- 完成状态

## 7. 设计调性

整体视觉保持：

- 轻盈
- 克制
- 有个人感
- 不像 SaaS 模板
- 不像开发后台
- 不像代码注释

动效可以有，但必须服务操作：

- 卡片悬停轻微上浮。
- 完成状态有轻反馈。
- 新增事项有柔和进入动画。
- 链接和子内容以轻标签、小列表或薄片呈现。

## 9. 文案与界面自证原则

页面应通过内容、层级和操作本身说明用途，不得用成段文字替界面辩解。普通前端页面禁止出现以下内容：

- 解释页面为什么存在、模块如何拼接、数据为何隔离的设计说明；
- 面向开发者的存储、安全、密钥、架构和实现说明；
- “这里……”“仍由……”“不会……”“负责……”式的系统自述；
- 为填满版面而写的口号、抽象价值句、成组三段式宣传语；
- 把本可由标签、状态、按钮表达的信息重新写成长句。

说明文字只在以下场景保留：输入格式无法从字段名判断、操作具有不可逆后果、错误需要给出恢复路径、空状态需要指出下一步。即使保留，也应短到能被一眼读完。

首页优先呈现可用信息：最近内容、搜索、栏目、常用工具和私人入口。装饰性首屏不得长期占据大部分视口，也不得让真实内容退到第二屏。安全、数据隔离和部署细节写入文档与测试，不放在日常界面中。新增前端文案必须通过 `ProductCopy.test.js` 的静态审计。

## 9. 首页与发布流精修约束

- 首页首屏优先展示真实内容、检索和常用入口，不以姓名、学历、学校或人格口号作为主视觉。
- 公开页头左侧必须承担返回首页和展示有效状态的作用，不保留纯字母 Logo 与重复站名占位。
- Preview 中的 OCR 与引注必须使用生产域名绝对地址，不能被解析为 Preview 自身路由。
- 最近内容必须具有稳定卡片边界、摘要与日期，不得退化为无层级的裸文本清单。
- Writing Studio 的保存按钮保持动作语义；成功提示短暂出现后恢复，不让“已保存”永久占据按钮。
- 写作发布设置在当前编辑环境内以弹窗完成，至少包含标题、摘要、类型、封面、栏目、合集、标签、slug 与访问方式。
- 文章和课程笔记共用服务端 AI 摘要入口。生成结果只用于填写可编辑摘要，用户确认后再保存或发布。
