# 课程回放自动获取、简报与笔记工程

更新时间：2026-06-29
状态：第一主工程设计基线，尚未开始平台接口实现

## 一、目标

课程平台通常在上课后约两天上传回放。用户可能因实习无法到场，因此系统不能只服务“听完课后整理”，而要主动维持课程连续性：发现新回放，取得用户有权访问的媒体，完成云端转写，先生成可在碎片时间阅读的课程简报，再进入现有完整笔记工作流，并把结果主动送到用户最可能查看的渠道。

完整链路：

```text
课程源登记
→ 用户授权会话
→ 定时发现新回放
→ 下载或流式读取媒体
→ 云端转写
→ 课程简报
→ 现有课程完整笔记流程
→ 统一归档
→ 微信优先 / 邮件备份推送
→ 回复写回对应课次
```

系统不额外制造“一分钟概览”。输出只保留两种有明确用途的尺寸：简报与完整笔记。

## 二、安全与授权边界

1. 只处理用户本人账号有权访问的课程与回放，不绕过访问控制、付费限制、DRM 或平台明确限制。
2. 登录令牌、JWT、Cookie、账号和密码都是 Secret。不得写入 Git、文档、截图、日志、URL 查询参数或前端可读配置。
3. 已经出现在聊天、日志或公开位置的令牌视为暴露，不继续作为长期凭据使用；实施时重新登录取得新会话。
4. 第一闭环采用“用户人工登录，系统接管已授权会话”。用户在教学网页正常完成登录并打开课程，捕获助手只读取必要会话与回放元数据。
5. 会话只在服务端加密或本地系统钥匙串中短期保存，同时保存过期时间。过期后进入 `awaiting_auth`，明确请求重新授权，不悄悄失败。
6. 不在第一闭环保存教学网明文账号密码。只有在确认平台许可、登录流程稳定且确有必要后，才评估由本地 helper 与系统钥匙串托管；服务器数据库不作为密码保险箱。
7. 调试样本必须脱敏。接口请求、响应和网络日志在分享前删除 Authorization、Cookie、JWT、学号及个人信息。

## 三、开始编码前必须取得的事实

课程平台部分不能靠猜测。需要先完成一次受控技术勘察：

- 同学制作的原链提取项目、用户脚本或关键代码；
- 登录后课程列表页面和一门真实课程回放页面；
- 课程列表、课次列表、回放详情与媒体地址对应的网络请求；
- 会话凭据来自 Cookie、JWT 还是两者组合；
- 令牌有效期、刷新方式、是否需要重新打开播放器；
- 媒体格式是 MP4、HLS/m3u8 还是其他形式；
- 是否存在动态签名、分片加密、频率限制或并发限制；
- 平台使用规则及个人学习用途的边界；
- 一门 60—120 分钟课程的媒体体积与转写时长。

技术勘察的输出是一份脱敏接口说明和一条可重复的手工命令，不把真实令牌放进仓库。

## 四、系统边界与运行位置

Vercel 和现有 Workflow 负责控制面：登记课程源、定时检查、状态机、重试、权限、成本记录及结果链接。长时间媒体下载、ffmpeg 音频提取和转写不放进普通 Vercel 请求。

媒体处理需要独立 Worker，候选形态包括：

- 用户本机轻量 helper：负责读取已登录会话和提取音频，重计算仍交给云端；
- 可持续运行的云端 Worker：负责下载、临时文件、音频提取和调用转写服务；
- 混合模式：本机只完成授权捕获，云端完成后续处理。

默认选择云端转写。本地 Whisper 仅作为可选后备，不要求 MacBook Air 长时间本地推理。ffmpeg 提取音频可以在本机 helper 或 Worker 完成，它远轻于本地运行语音模型。

## 五、内容模型

### 1. 课程源 `course_sources`

每门被监测课程一条记录：

- `owner_id`
- `source_type`
- 平台课程标识及展示名称
- 学期、教师、预期上课时间
- 检查频率和最后检查时间
- 处理模式：`brief_and_note` 或 `brief_only`
- 当前授权状态与会话过期时间
- 最近成功课次及最近错误

### 2. 回放记录 `course_replays`

每次平台回放一条记录：

- 外部回放 ID、课程源、课次时间和上传时间；
- 回放页面及媒体元数据；
- 去重指纹；
- `discovered / awaiting_auth / queued / transcribing / briefing / note_processing / ready / failed`；
- 转录引用、简报、对应 `course_job` 与 `lesson_key`；
- 重试次数、最近错误和成本统计；
- 原始媒体删除时间。

同一外部回放 ID 或指纹只能创建一个处理任务。定时检查和人工重试都必须幂等。

### 3. 复用现有课程层级

新回放不得创建平行的“简报库”。它应进入现有结构：

```text
课程
  └─ 课次
       ├─ 回放来源与时间
       ├─ 转录
       ├─ 简报
       ├─ 完整笔记
       ├─ 推送记录
       └─ 用户补充
```

`lesson.brief` 服务碎片化阅读，`lesson.finalNote` 继续作为系统性笔记事实来源。笔记库按课程和课次展示，通过状态和筛选区分简报可读、笔记处理中和完整笔记可读。

## 六、输出定义

### 课程简报

简报需要在转录完成后优先生成并推送，结构稳定但不模板腔：

- 课程、课次、上课日期与回放上传时间；
- 本课主线；
- 三至五个核心问题；
- 老师明确赞成、反对、反复强调或提示考试的内容；
- 重要案例、法条和材料；
- 与前课、后续课程或既有知识的关系；
- 完整简报和笔记状态链接。

简报应能在五至十分钟内读完。消息正文只展示最关键内容，完整版本在站内阅读。

### 完整笔记

完整笔记复用已有课程流程：材料映射、大纲、节点写作、独立审查、必要修订、拼装与人工确认。自动回放接入只负责创建可靠转录和课次，不另造第二套笔记生成器。

课程级设置决定是否在简报后自动进入完整笔记。失败不影响已经生成的简报。

## 七、原始文件与存储

不长期保存课程视频。处理原则：

1. 获取回放后下载或流式提取音频；
2. 将音频送入云端转写；
3. 保存转录、时间戳、回放元数据、简报、笔记和必要来源定位；
4. 转写成功并通过完整性检查后删除原始视频和临时音频；
5. 失败时按短 TTL 保留临时文件用于重试，随后自动清理。

原回放仍由教学平台保存。本站记录来源页面和课次标识，供用户在权限仍有效时返回核验。

## 八、推送与回复

### 渠道顺序

- 微信：最终首选渠道；
- 邮件：可靠备份和当前已具备的通道；
- 站内：完整阅读、历史与管理事实来源。

课程工程在“微信回复闭环”完成前不能被描述为最终完成，邮件不是用来永久替代微信的借口。但在微信通道研究期间，第一闭环仍必须通过邮件真实送达，确保处理链本身已经可用。

### 统一消息记录

每次发送保存：

- `owner_id`
- 渠道、接收目标及外部消息 ID；
- 主题、课次、发送时间和状态；
- 站内对象及链接；
- 是否已打开或回复（渠道支持时）；
- 回复写入的目标记录。

微信或邮件回复必须能关联原消息。课程简报回复写入该课次的用户补充；Today 回复写入当天记忆草稿。无法可靠关联时进入 Inbox，不静默丢失。

### 防止再次成为小号坟场

- 消息正文控制长度，只突出本课主线、关键点及一个明确入口；
- 同一课次不重复发送成功通知；
- 失败、重新授权和紧急截止使用不同优先级；
- 可以按课程设置即时发送或每日合并；
- 站内保留未读、已读、稍后和已处理状态；
- 定期回顾只重新呈现少量真正未处理内容。

## 九、三个可独立使用的闭环

这些不是“搭壳、以后再补”的开发阶段。每一个闭环都必须能独立长期使用。

### 闭环 A：授权人工导入

用户登录教学网并打开一门课，捕获助手取得必要授权和回放元数据。系统完成一节真实回放的媒体获取、云端转写、简报、完整笔记和邮件送达。

验收：

- 真实回放成功，不使用样例数据；
- JWT/Cookie 不出现在日志、Git 和前端；
- 简报可在站内读取并通过邮件送达；
- 完整笔记进入原课程及课次；
- 原始媒体在成功后清理；
- 重复运行不生成重复课次；
- 任一步失败有状态、原因和重试入口。

即使后续自动监测尚未开发，这一闭环也已经能够替代手工下载、转写与整理。

### 闭环 B：自动发现新回放

登记一门课程后，系统定时检查回放列表，发现新课次并自动执行闭环 A。授权过期时只请求重新登录，不删除旧结果或制造重复任务。

验收：

- 连续监测至少一门真实课程；
- 新回放上传后在约定检查周期内被发现；
- 未上传时不产生空任务；
- 授权过期可恢复；
- 多次检查与重试保持幂等；
- 简报主动送达。

### 闭环 C：学期可靠运行与微信回复

多门课程同时运行，提供课程源管理、失败重试、成本统计、消息历史、微信推送与回复写回，并完成至少数周真实使用验证。

验收：

- 多课程、跨课次内容不串联；
- 简报、笔记与推送在一个课程层级中清楚可找；
- 微信回复能进入原课次；
- 邮件作为备用通道可切换；
- 本月转写和模型费用可见；
- 服务异常能够说明影响范围；
- 周期性运行没有静默漏课和重复消费。

## 十、成本与可靠性

- 转写和简报分别记录 provider、模型、用量、耗时与估算费用；
- 一门课在执行前可估算音频时长和成本；
- 简报使用较低成本模型，完整笔记保留高质量模型；
- 转录 provider 通过统一 adapter 接入，先对一节 60—120 分钟真实课程做质量、耗时和价格基准；
- 下载、转写、简报和笔记各自可重试，不能整条链从头重复消费；
- 处理任务使用确定性外部 ID 和 checksum 去重；
- 任何失败不得覆盖已有简报或最终笔记。

## 十一、第一轮研究与设计任务

在写数据库迁移和页面前，先完成：

1. 取得并审查同学的原链提取项目；
2. 在本机以正常登录方式记录一门课程的脱敏网络流程；
3. 确认课程列表、回放列表、详情和媒体接口；
4. 测试令牌过期及重新授权；
5. 用一节真实课程验证媒体格式和音频提取；
6. 选择两种云端转写候选并做质量、耗时、成本对照；
7. 确定微信发送与回复所依赖的现有机器人/公众号通道；
8. 画出课程源、回放、现有 course job/lesson 和消息记录之间的数据映射；
9. 再决定 Worker 部署位置与第一份数据库迁移。
