**状态：产品宪法／v2 权限分层修订稿**
**日期：2026-07-03**
**适用范围：微信 ClawBot、Law-Tech 网站后台及后续所有自然语言控制入口**

> 2026-07-04 修订：本文的自然语言优先、模型不得直接 SQL、真实对象、Resource/Tool 分离、风险门禁和结构化上下文原则继续有效。下文原 v1 `Router → capability` 示例已被真实微信事故证明不足；凡与本修订冲突，以本修订和 `DECISIONS.md` D-015—D-018 为准。

## v2 权限分层修订

新的稳定主链路是：

```text
Message
→ UserIntent（模型输出，不含 capability/tool/risk/SQL）
→ Deterministic Planner（代码选择注册能力）
→ Semantic Gate（代码检查语义一致性）
→ Resource / Entity Resolution（只读真实候选）
→ Risk Policy（风险由 Capability Card 派生）
→ Tool（命名工具和真实 ID）
→ Response（只依据工具结果）
→ Trace
```

`UserIntent` 描述用户要做什么、作用于什么对象、提取了哪些字段、引用了什么上下文以及仍有哪些不确定项。模型不能在这一阶段输出 capability 或工具名。

`RoutePlan` 改为代码产物，不再是模型的直接执行指令。Planner 只能从已发布的版本化 Capability Registry 选择能力；Semantic Gate 必须检查 action、domain、objectType、scope 与能力卡一致。`agent.help`、只读、写入和删除都必须经过同一语义门禁，不能存在提前返回的权限旁路。

首个交付闭环是完整 Agent Studio + Evaluation Kernel，不接入真实微信；随后才是 default-off、无 Tool 的 Production Shadow。任何 Canary 均为后续独立 PR。

截至 2026-07-04，v2 contracts、受约束 AgentProfile、150 条固定评估集、Studio 与 additive database boundary 已在独立分支实现并通过隔离数据库事务验收；在 PR、Preview、真实配置模型评估和 Production migration 完成前，状态仍是“实现中”，不是已发布能力。

## 一、产品定义

Law-Tech 微信 AI Agent 不是关键词机器人，不是一个把微信消息机械转发到数据库的保存接口，也不是允许模型直接操作数据库的自由代理。它应当被定义为：

> **Law-Tech 的自然语言控制平面。用户可以在微信中以日常、自由、上下文连续的语言表达意图；系统负责理解意图、选择能力、读取真实数据、解析具体对象、安全执行操作，并以自然语言报告结果。**

微信是主要交互入口，网站是数据、内容和可视化工作台，Agent 是连接两者的智能控制层。用户不应学习固定命令模板，也不应为了配合系统而记住“先查询、再选序号、再发送固定词语”的仪式。系统应适应用户，而不是反过来。

产品最终应满足三个核心承诺：

1. **说人话就能用。** 同一个意图可以有大量自然表达，系统理解语义而不是依赖关键词完全一致。
2. **能理解，但不会乱动。** 模型负责理解和提出操作计划，代码负责校验、权限、确认和执行。
3. **可以持续长大。** 新增轻知识、内容推荐、系统状态、AI 指标或未来其他能力时，只新增资源和工具，不推翻主链路。

## 二、不可更改的产品原则

以下原则构成产品宪法。后续可以替换模型、数据库、框架或服务，但不能违反这些原则。

### 1. 自然语言优先

任何用户可合理表达的自然语言，都应进入模型语义理解层。不得要求用户学习固定句式，也不得以正则表达式作为主要意图分类器。

正则表达式只允许用于：

- 空消息、长度、URL、UUID、日期格式等基础校验；
- outbound、自身消息、系统消息等传输层过滤；
- 已经由模型确定意图后的确定性字段归一；
- 安全策略中的不可绕过边界。

正则不得决定“用户究竟想做什么”。

### 2. 模型理解，代码执行

模型可以：

- 理解意图；
- 识别领域与操作；
- 生成结构化计划；
- 从真实候选中选择对象；
- 决定还需要读取哪些信息；
- 根据工具结果编写回复。

模型不得：

- 直接连接数据库；
- 自由编写并执行 SQL；
- 编造数据库 ID、表名或字段；
- 绕过权限、确认和风险策略；
- 在没有真实工具结果时宣称操作成功。

### 3. 真实对象先于写入

任何修改必须最终落到真实、经过验证的对象 ID 上。用户说“国际法六月三号的笔记”时，模型负责理解和生成检索条件；检索层返回真实候选；只有唯一或明确选中的真实对象才能被修改。

模型的猜测永远不能直接变成数据库写入。

### 4. 读取资源与执行工具分离

所有能力分为两类：

- **资源（Resource）**：只读地提供网站、数据库、课程、内容、系统和外部世界的信息；
- **工具（Tool）**：执行创建、修改、完成、标记已读、删除、同步、重试等操作。

读与写必须在接口层分开。资源可以被自由检索；工具必须经过风险策略和参数校验。

### 5. 歧义时澄清，不猜测，也不静默吞掉

当存在多个近似对象且无法唯一判断时，系统应列出最少的必要候选，让用户选择。不得猜一个执行，也不得只回复“未识别到需要处理的内容”。

系统必须区分：

- 没有操作意图；
- 有操作意图但缺少对象；
- 找不到对象；
- 找到多个对象；
- 模型或工具暂时不可用。

每一种情况都应给出有意义的回应。

### 6. 风险与确认成比例

不是所有写操作都需要打断用户确认，也不是所有写操作都能自动执行。风险按操作性质分级：

- 只读：自动执行；
- 可逆、明确、唯一对象的写入：自动执行；
- 明确的批量可逆操作：自动执行并报告数量，提供撤销能力；
- 删除、清空、不可逆操作：执行前确认；
- 服务重启、部署、数据库迁移、密钥和权限操作：强制确认、权限校验和审计。

### 7. 上下文是结构化状态，不只是聊天记录

“这个”“刚才那个”“时间改到十点”等表达必须通过结构化上下文解析。系统不能只把上一句话拼到下一句话前，也不能仅依赖一个十分钟 TTL 的 lastObject。

上下文必须保存真实对象引用、候选集合、待确认操作和主题焦点。

### 8. 新能力通过注册接入，不修改总路由

每个新功能必须以“能力卡片”的方式注册，包括能力名称、说明、输入输出、数据来源、风险等级和确认规则。总路由器通过能力目录选择工具，不需要为每个新功能新增一组关键词。

### 9. 无模型时不猜着写

模型、网络或工具不可用时：

- 不得退化为正则猜测并写数据库；
- 可以执行明确、安全的系统固定功能；
- 其余情况应说明暂时无法理解或执行；
- 已有定时任务和确定性自动化不受影响。

### 10. 每次操作都可解释、可追踪、可复盘

系统应记录一条完整轨迹：

> 收到什么消息 → 读取了哪些上下文 → 选择了什么能力 → 检索到哪些候选 → 为什么执行或澄清 → 调用了什么工具 → 工具返回什么 → 最终如何回复。

敏感信息必须脱敏，但不能因为追求简洁而失去可审计性。

## 三、总体架构

```text
微信消息
  ↓
0. 接入与传输安全层
  ↓
1. 上下文装配器
  ↓
2. 快速语义路由器
  ↓
3. 能力注册表与工具选择
  ↓
4. 资源检索与实体解析
  ↓
5. 操作规划器
  ↓
6. 风险策略与确认门禁
  ↓
7. 确定性执行器
  ↓
8. 回复生成器
  ↓
9. 会话记忆、事件日志与评估
```

这条主链路原则上不再改变。未来能力只在第 3、4、7 层增加新的资源适配器和工具。

## 四、各层职责

### 0. 接入与传输安全层

负责与语义无关的确定性工作：

- 鉴权；
- sender 白名单；
- messageId 幂等；
- outbound、自身、assistant、system 消息过滤；
- 消息长度和格式限制；
- 基础时间、渠道、线程信息记录；
- 保存原始消息和 traceId。

这一层不得判断“读完”“提醒”“课程”等词的业务含义。

### 1. 上下文装配器

给路由模型提供小而准确的上下文，不把整个数据库或全部聊天记录塞进提示词。默认包含：

- 当前消息；
- 当前时间、时区和用户身份；
- 最近 4—8 个语义相关对话轮次；
- 当前主题焦点；
- lastSelected、lastCreated、lastUpdated 等真实对象引用；
- 最近一次候选集合的简要信息；
- 待确认操作；
- 能力注册表的紧凑摘要。

上下文装配器只提供“当前理解所需的最小信息”。

### 2. 快速语义路由器

路由器使用快速、低延迟、支持严格结构化输出的模型。它不是最终执行者，只输出统一的 RoutePlan。

推荐结构：

```json
{
  "version": 1,
  "decision": "act | retrieve | answer | clarify | ignore",
  "domain": "course",
  "capability": "course.brief.mark_read",
  "operation": "update",
  "scope": "single | selected | matching | all_unread",
  "target": {
    "ids": [],
    "query": "国际法 2026-06-03",
    "contextRefs": []
  },
  "parameters": {},
  "sourcePreference": "internal | public | auto",
  "risk": "read | reversible_write | bulk_write | destructive | privileged",
  "confidence": 0.96,
  "needsRetrieval": true
}
```

路由器使用多维结构，而不是一个不断膨胀的扁平“意图枚举”。新增功能通常只增加 capability，不需要增加新的总分类逻辑。

### 3. 能力注册表

每项能力由一张能力卡片定义：

```text
id: course.brief.mark_read
domain: course
description: 将一份或多份课程简报标记为已读
mode: write
inputSchema: target IDs / scope
outputSchema: updated objects / count
dataSource: CourseBriefResource
risk: reversible_write
confirmation: explicit bulk scope can execute; destructive variants require confirmation
idempotent: true
version: 1
```

路由器只看到紧凑的能力名称和一句话说明。选中能力后，再加载完整工具 schema。这样能力越多，首次意图识别的上下文也不会无限增长。

第一阶段可以在当前 Node/Next.js 架构内实现内部能力注册表；接口设计保持 MCP 兼容，但没有必要为了形式完整立刻部署一套 MCP 基础设施。

### 4. 资源检索与实体解析

路由完成后，系统才读取相关领域的数据。不得在第一层把全部日程、课程和文章塞给模型。

实体解析采用混合检索：

1. 稳定 ID 和上下文引用；
2. 标题、课程名、日期、别名的规范化匹配；
3. 全文或 trigram 模糊匹配；
4. embedding 语义检索；
5. 业务字段约束与排序。

例如：

```text
用户：国际法六月三号的笔记读完了
路由：course.brief.mark_read
检索条件：
  course≈国际法
  lessonDate≈2026-06-03
  read=false
候选：
  国际法学 · 2026-06-03第5-6节
```

若唯一高置信匹配，直接执行；若两个候选接近，向用户澄清；若没有候选，明确说明没有找到，而不是创建一条新 Reading。

### 5. 操作规划器

简单请求不需要再次调用大型模型。路由器已经给出唯一工具和参数时，直接进入安全门禁。

复杂请求才进入规划器，例如：

- 一句话包含多个操作；
- 需要跨领域读取后再决定；
- “找一篇与我最近课程相关的公开文章，摘要后加入待读”；
- “本周哪些课程更新了但我还没读，把最重要的两篇推给我”。

规划器可以调用多个只读资源，再生成受约束的工具计划。默认保持一个主 Agent 负责最终回复，领域能力作为工具；只有在领域拥有完全不同的提示词、权限和策略时，才拆分专门 Agent。

### 6. 风险策略与确认门禁

风险门禁位于模型理解之后、工具执行之前。它不负责理解语言，只检查结构化计划。

#### R0：无操作或闲聊

例如“今天心情不错”。正常回应或静默均可，由产品交互策略决定，但不得写数据库。

#### R1：只读

例如查询日程、课程更新、服务器状态、随机推荐。自动执行。

#### R2：明确的可逆写入

例如新增日程、修改时间、标记一份简报已读。目标唯一且用户意图明确时自动执行。

#### R3：明确的批量可逆写入

例如“未读课程简报已全部读完”。范围明确时自动执行，回复具体数量，并提供可撤销记录。

#### R4：破坏性操作

删除、永久清空、批量取消等操作必须确认。

#### R5：高权限系统操作

部署、重启服务、数据库迁移、恢复备份、修改密钥或权限，必须经过显式确认、权限校验、审计和回滚计划。微信端默认只允许查询状态，不直接执行生产运维，除非未来专门开放受控能力。

### 7. 确定性执行器

模型不编写 SQL。执行器只接受版本化的结构化工具调用。

读取使用 QuerySpec：

```json
{
  "resource": "course_brief",
  "filters": {
    "course": "国际法",
    "lessonDate": "2026-06-03",
    "read": false
  },
  "sort": [{"field": "updatedAt", "direction": "desc"}],
  "limit": 5
}
```

写入使用 MutationSpec：

```json
{
  "tool": "course.brief.mark_read",
  "targetIds": ["真实对象ID"],
  "patch": {"read": true},
  "preconditions": {"read": false},
  "idempotencyKey": "wechat:sender:messageId"
}
```

执行器负责：

- 参数校验；
- 权限校验；
- 真实 ID 校验；
- 事务；
- 并发版本与前置条件；
- 幂等；
- before/after 快照；
- 撤销信息；
- 审计日志。

复杂跨表查询由服务端资源适配器、数据库视图或受控查询函数实现，不由模型自由生成 JOIN。

### 8. 回复生成器

回复必须基于真实工具输出。简单操作优先使用准确的确定性模板，复杂查询和推荐再交给模型组织语言。

回复至少应说明：

- 做了什么；
- 操作了哪个对象或多少个对象；
- 结果是否全部成功；
- 相关链接；
- 是否可以撤销；
- 若失败或歧义，下一步需要用户补充什么。

禁止使用没有信息量的兜底句，例如“未识别到需要保存的内容”。应改为具体错误：

- “我理解你想标记课程简报已读，但没有找到 6 月 3 日的国际法简报。”
- “我找到了两份可能的国际法简报：……你指哪一份？”
- “意图理解服务暂时不可用，因此没有执行任何写入。”

### 9. 会话记忆与事件日志

上下文应分为四类存储。

#### 会话原始轮次

保存有限的近期用户消息、回复和工具结果，用于自然对话。模型默认只取最近 8—12 轮，而不是无限追加。

#### 结构化会话状态

保存：

```text
activeTopic
lastSelectedObject
lastCreatedObject
lastUpdatedObject
lastResultSet
pendingPlan
pendingConfirmation
resolvedReferences
```

所有对象引用保存真实 ID、类型、标题和版本。

#### 长期用户记忆

只保存稳定偏好和明确要求长期记住的内容，例如偏好的推荐主题、回复长度、常用课程别名。不得把短期操作对象误写成长久记忆。

#### Agent 运行轨迹

保存 route、resource query、candidate resolution、tool call、policy decision、latency、token usage 和最终结果。敏感字段脱敏。

建议默认时效：

- 破坏性确认：10 分钟；
- 最近候选集合：30 分钟；
- active focus：2 小时或发生明确主题切换前；
- 近期对话窗口：最近 8—12 轮；
- 长期偏好：用户明确保存或达到严格稳定条件后持久化。

“这个读完了”只能使用仍有效且唯一的 active focus；若上下文已经切换或对象不唯一，则澄清。

## 五、领域与能力目录

意图不应只按“增删改查”分类，而应由领域、能力和操作共同构成。

### 1. 日程与任务 Schedule

读取：

- 今日、明日、本周、逾期和全部待处理；
- 搜索、统计、比较；
- 某段时间有哪些安排；
- 提醒状态。

写入：

- 创建、修改、完成、取消、归档；
- 设置日期、时间、地点、重复和提醒；
- 批量调整；
- 撤销最近一次修改。

### 2. 阅读 Reading

对象主要是收藏文章、材料、链接和待读内容。

能力包括：

- 保存文章或链接；
- 搜索和列出；
- 标记已读/未读；
- 修改摘要、标签或阅读时间；
- 随机选择一篇；
- 按主题、时间、来源或课程关联推荐；
- 将公开网页加入待读。

### 3. 课程 Course

课程不是普通 Reading 的同义词。它有课程、课次、课程简报、最终笔记和流水线状态等独立对象。

能力包括：

- 查看本周更新课程；
- 查询某课程或某课次；
- 查看未读课程简报；
- 单个、多个或全部标记已读；
- 查询笔记生成和课程处理状态；
- 推送一份课程简报；
- 将课程内容转成轻知识、待读或写作素材。

### 4. 轻知识 Knowledge

轻知识是独立领域，不得硬塞进 Reading 或日程。

建议对象类型：

- idea：想法；
- fact：事实或知识点；
- question：待研究问题；
- quote：引文；
- concept：概念；
- observation：观察；
- connection：对象之间的关联。

基础字段：

```text
title
body
kind
source
sourceObjectId
tags
relations
status
createdAt
updatedAt
```

能力包括：

- 快速记录；
- 自动提炼标题和标签；
- 搜索、回忆、关联；
- 扩写；
- 转为 Reading、日程、文章素材或课程笔记；
- 随机复习和周期回顾。

### 5. 内容与发布 Content

包括网站公开文章、公开笔记、草稿和其他可发布内容。

能力包括：

- 搜索网站已发布内容；
- 获取正文或摘要；
- 推荐一篇公开内容；
- 查看最近更新；
- 将内部材料转为草稿；
- 查询发布状态。

公开内容未必全部存储在同一数据库中，因此通过 ContentResource 统一读取，底层可以连接 Notion、内容快照、数据库或静态文件。

### 6. 跨域工作台 Workspace

处理“今天整体怎么样”“最近我在忙什么”“本周有哪些课程更新但还没读”等跨领域问题。

它调用多个只读资源并聚合，不直接拥有自己的业务数据。

### 7. 系统与基础设施 System

只读能力优先：

- Gateway、Relay、Cloudflared、Vercel、数据库等健康状态；
- 最近部署；
- 备份状态；
- 队列和流水线积压；
- 错误和告警摘要。

系统状态不得靠模型自由执行 shell 获取。应由受控的 Health Provider 周期采集或实时调用白名单健康接口，生成统一的 SystemSnapshot。

生产写操作默认不从普通微信对话开放。

### 8. AI 与自动化 AI

能力包括：

- 当前模型和不同任务的模型配置；
- token、成本、调用量和缓存命中；
- 最近模型错误；
- 课程 AI 流水线状态；
- 调度器和自动化状态；
- 在权限允许时触发安全的重试。

现有模型配置应扩展为：

```text
router
planner
responder
embedding
schedule
brief
writer
reviewer
revision
finalReview
```

路由和简单规划优先使用低延迟模型；复杂跨域规划才升级到更强模型。

### 9. 外部信息与推荐 External

能力包括：

- 搜索公开网页；
- 推荐公开文章；
- 获取当前信息；
- 对外部内容摘要；
- 保存到 Reading 或轻知识。

外部信息必须标明来源和时间。只读搜索与保存操作分开；搜索结果不会自动写入数据库，除非用户明确要求保存。

### 10. Agent 自身 Agent

能力包括：

- 查看当前支持什么；
- 查看或清除当前上下文；
- 撤销最近操作；
- 管理长期偏好；
- 解释刚才做了什么；
- 切换对话主题；
- 报告无法执行的原因。

## 六、现有数据与未来数据接入

目前已经可以确认：

- 日程和普通 Reading 由 schedule 数据源读取；
- 课程简报来源于 course jobs 中的课程工作流数据；
- 课程简报已读状态有独立状态数据；
- Today Snapshot 已经能够汇总日程、Reading 和课程简报；
- 当前对话状态已有数据库存储，但结构和时效不足以承担完整 Agent 记忆。

公开文章、网站笔记、系统指标、AI 使用记录等数据是否全部已有统一数据库来源，需要单独做数据资源盘点。目标架构不要求所有数据强行迁入同一张数据库，而要求每个数据源提供统一 Resource Adapter。

所有领域对象同时写入一个**派生搜索索引**，建议字段包括：

```text
objectType
objectId
title
aliases
searchText
tags
source
updatedAt
permissions
embedding
```

搜索索引只用于检索和实体解析，不是业务事实的最终来源。修改仍然回到原领域工具执行。

## 七、延迟与成本设计

系统采用“自适应深度”，不是每条消息都运行完整多 Agent 流程。

### Level A：直接工具调用

适用于明确、简单、单领域命令：

- “明天十点开会”
- “未读课程简报全部读完”
- “今天有什么安排”

流程：一次快速模型调用 → 一个工具 → 回复。

### Level B：检索后执行

适用于需要对象匹配：

- “国际法六月三号那篇读完了”
- “把周五的会改到三点”

流程：快速路由 → 资源检索 → 唯一解析 → 工具 → 回复。

### Level C：多工具规划

适用于跨域或外部任务：

- “找一篇和我这周国际法课程相关的公开文章，摘要后加入待读”
- “本周更新了哪些课，挑两份最值得先读的简报给我”

流程：路由 → 多资源读取 → 规划 → 工具组合 → 回复。

建议工程目标：

- 路由 p50 不超过 0.8 秒，p95 不超过 1.8 秒；
- 简单单工具请求 p50 不超过 2.5 秒，p95 不超过 5 秒；
- 复杂多资源或公开网页任务 p95 不超过 12 秒；
- 超过合理时间时允许先返回简短进度状态，但不得宣称未完成的操作已成功。

优化方法：

- 静态系统提示和能力摘要放在提示词前部；
- 用户消息和动态上下文放在后部；
- 使用提示缓存；
- 不提前加载全部工具 schema；
- 独立只读资源并行获取；
- 简单结果采用模板回复；
- 系统状态和统计数据适度缓存。

## 八、上下文工作示例

### 示例一：批量课程简报

```text
用户：未读课程简报已全部读完
```

路由：

```json
{
  "decision": "act",
  "domain": "course",
  "capability": "course.brief.mark_read",
  "scope": "all_unread",
  "risk": "bulk_write"
}
```

资源返回当前四份未读简报的真实 ID。策略确认该范围由用户明确表达，操作可逆，因此直接执行。回复：

```text
已将 4 份未读课程简报全部标记为已读。
```

并记录撤销信息。

### 示例二：自然标题匹配

```text
用户：国际法六月三号的笔记读完了
```

系统检索课程名、课次日期和标题别名，唯一匹配：

```text
国际法学 · 2026-06-03第5-6节
```

执行标记已读。用户不需要写出数据库中的完整标题。

### 示例三：指代上一对象

```text
用户：给我看看国际法六月三号的笔记
Agent：……内容……
用户：这个读完了
```

第二轮通过 active focus 中的真实 course brief ID 直接执行。

### 示例四：修改上一日程

```text
用户：后天上午九点提醒我去开会
Agent：已创建……
用户：时间改到十点
```

第二轮使用 lastCreatedObject，更新该对象，不创建新日程。

### 示例五：随机内部推荐

```text
用户：随便找一篇待读推给我
```

调用 `reading.sample`，根据未读状态和可选偏好随机选择，不访问外网。

### 示例六：公开内容推荐

```text
用户：随便找一篇公开发布的法律文章推给我
```

调用 external search，返回来源和摘要。只有用户继续说“加到待读”时才调用 reading.create。

### 示例七：系统状态

```text
用户：现在服务器、数据库和 AI 状态怎么样
```

调用 SystemSnapshot、DatabaseSnapshot 和 AiSnapshot，返回经过采集的真实状态；模型只负责组织回复。

### 示例八：轻知识

```text
用户：记一个想法，证据关门不应该只是期限规则，它其实也在重新分配侦诉审之间的失败成本
```

路由到 `knowledge.capture`，保存为 idea。后续：

```text
用户：把刚才那个想法扩成一个论文论证提纲
```

使用 lastCreatedObject 读取原文并调用知识扩写工具。

## 九、失败与降级策略

### 模型调用失败

- 不执行任何需要语义判断的写操作；
- 返回“意图理解服务暂时不可用，本次没有修改数据”；
- 确定性定时任务和已有自动化继续运行。

### 资源读取失败

- 不让模型自行补全数据；
- 明确说明哪个数据源不可用；
- 多源查询可返回其余成功部分，并标注缺失。

### 写工具部分失败

- 使用事务时全部回滚；
- 无法事务化的批量操作返回成功和失败对象清单；
- 回复不能只说“已完成”。

### 对象匹配歧义

- 返回最相关的 2—4 个候选；
- 允许用户用序号、标题片段或自然语言继续选择；
- 候选集合进入结构化上下文。

### 无匹配对象

- 不创建同名新对象；
- 说明理解到的意图和未找到的目标；
- 允许用户修改条件或明确要求新建。

质量指标：

- Preview 和真实微信验收必须包含自然改写，不只测试原句。

## 十一、现有系统的保留、废止与新增

### 保留

- 微信 Relay 的鉴权、消息转发和自身/outbound 过滤；
- messageId 幂等；
- 现有日程和 Reading 数据模型；
- course brief 读取与已读状态函数；
- Today Snapshot；
- 已有用户模型配置与加密密钥存储；
- 已有领域业务函数和数据库权限。

### 废止或降级

- `classifyCommandText` 不再作为最终意图权威；
- `mutationPolicy` 不再以关键词决定用户语义；
- `/api/schedule/capture` 不再承担所有未知命令的万能兜底；
- 不再要求“先查询—选序号—固定命令”才能操作；
- 不再把整个用户句子保存为 Reading 标题作为 fallback；
- 不再允许规则 fallback 在模型失败时猜测写入。

关键词和规则可以保留为特征、校验或测试辅助，但不能覆盖模型的结构化语义计划。

### 新增

- Agent Controller；
- Capability Registry；
- Resource Adapter 层；
- RoutePlan schema；
- QuerySpec / MutationSpec；
- hybrid entity resolver；
- 结构化会话状态；
- 统一派生搜索索引；
- Tool Policy / approval engine；
- Agent trace 与评估数据集；
- 撤销和 before/after 事件记录。

## 十三、架构冻结规则

本纲领分为三层：

1. **产品宪法**：本文第二部分和总体主链路，原则上冻结；
2. **稳定协议**：RoutePlan、Capability Card、QuerySpec、MutationSpec，采用版本号和向后兼容演进；
3. **能力目录**：可以持续新增、停用或升级。

未来提出新需求时，首先判断它属于哪个资源和能力。只有确实无法放入本架构时，才能提出架构修订；不能为了实现一个句式或一个功能，再在总路由里增加临时正则分支。

## 十四、最终决策

Law-Tech 微信 Agent 采用：

> **单一主控 Agent + 动态能力注册表 + 只读资源 + 受控工具 + 结构化会话状态 + 风险门禁 + 全链路追踪。**

不采用：

- 关键词优先的命令解析器；
- 模型直接 SQL；
- 一开始就拆成大量互相转交的 Agent；
- 每次把全库和全部历史塞入上下文；
- 模型失败时用规则猜着写；
- 新增一个功能就修改总分类器。

后续所有实现均以此纲领为唯一产品与技术方向。

## Phase 1 稳定接口落地（2026-07-03）

- `RoutePlan`：模型唯一输出，包含 decision/domain/capability/operation/scope/target/parameters/risk/confidence；

- `Risk Policy`：read、reversible_write、bulk_write、destructive、privileged 五级；
- 代码位置：`lib/openclaw/agent/*`；HTTP 入口：`pages/api/integrations/openclaw/command.js`；验收 trace：`pages/api/integrations/openclaw/traces.js`。
