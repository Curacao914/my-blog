# haoke-notes 网页端适配策略

## 边界

不修改本地 Claude Code 中的 `haoke-notes` Skill。

网页端只做一个适配层：

- 收集课程 job。
- 管理材料包。
- 保存用户偏好。
- 驱动后端 Worker 按 Skill 流程运行。
- 把中间确认点搬到网页。

## 材料包模型

实际课程有两种常见形态：

- 一份 SRT 对应多份 PPTX。
- 多份 SRT 对应一组连续课次，并共享同一门课的上下文。

因此网页端不做一对一配对。一个课程 job 默认表示一门课或一组连续课次的整理批次：

```text
course_job
├── transcript: N 个 SRT，至少 1 个
├── slides: N 个 PPTX，可多个
├── reading: N 个 PDF / Markdown / 文档
└── supplement: N 个图片 / 其他补充材料
```

上传阶段只要求这些材料属于同一门课或同一批连续课次，不要求人工逐页配对。

## 处理策略

第一步先把所有材料预处理为文本，并建立课次映射：

```text
SRT 1 → transcript text → lesson 1
SRT 2 → transcript text → lesson 2
PPTX 1 → ppt_md_1
PPTX 2 → ppt_md_2
PDF / Markdown → reading text
→ lesson_map.json
```

如果 PPTX 是图片型，再进入 OCR。

然后生成材料索引：

```text
每份 PPTX 的标题、页码、章节、关键词
每份阅读材料的标题、段落、关键词
```

模型阶段使用：

```text
当前课次转录稿全文
+ 多份 PPTX 的文本 / 索引
+ 阅读材料索引
+ 前序课次的摘要 / 概念索引
→ 自动判断材料和讲授内容的对应关系
```

也就是说，网页端不强制 SRT-PPT 一对一；模型可以基于足够上下文自行对齐。

## 多课次顺序运行

当一个 job 上传了多份 SRT 时，Worker 必须按课程序号顺序串行处理：

```text
lesson 1
→ 生成单课笔记
→ 提取本课摘要 / 概念 / 法条 / 案例 / 易混点
→ 作为 previous_context 传给 lesson 2
→ lesson 2
→ ...
```

上下文连续性不靠把所有课次一次性塞进同一个 prompt，而是靠可控的滚动上下文：

- 上一讲的笔记概览。
- 已出现概念表。
- 已出现法条表。
- 老师固定术语和译名。
- 本课程已经形成的结构框架。

这样既保留连续性，也避免后面某一讲被前面全部正文淹没。

## 用户确认点

网页端保留三个确认点：

1. 材料包确认
   - 是否有至少一个 SRT。
   - 多份 SRT 的课次顺序是否正确。
   - 多份 PPTX 是否都属于这一课程批次。
   - PPTX 顺序是否大致正确。
   - 是否有明显无关文件。

2. preflight 偏好确认
   - 老师姓名。
   - 讲课风格。
   - 学习目标。
   - PPT 类型。
   - 笔记详略。

3. 大纲确认
   - 大纲结构。
   - 每个节点对应的转录稿范围。
   - 相关 PPTX / 页码提示。
   - 是否合并、拆分、删除节点。

## 单课笔记生成策略

网页端 Worker 仍沿用 Skill 的大纲驱动策略，但把确认点产品化：

```text
材料包确认
→ preflight 偏好确认
→ 预处理多份 SRT / PPTX / OCR
→ 生成 lesson_map.json
→ 按课次顺序生成 outline.json
→ 网页端逐课确认大纲
→ 按二级节点逐节生成单课笔记
→ 节点过大时再拆三级节点
→ 拼装为单课 Markdown
→ verify_notes.py 校验
```

关键原则：

- 大纲骨架优先以 PPT 逻辑为锚；多份 PPTX 按用户排序和模型索引共同决定顺序。
- 转录稿用于填充老师实际讲授、案例、强调、发散内容。
- PPT 提及但课堂未展开的内容要标注“PPT 提及但未展开”。
- 转录中讲到但 PPT 没有的内容归入语义最近的 PPT 节点。
- 每个二级节点单独生成并落盘，避免一次性长输出失控。
- 节点对应转录超过阈值时继续细分。
- 最终拼装阶段不重新大规模改写，只做概览、顺序、META 汇总和格式校验。

## 渐进式披露策略

全课程整合阶段不一次性读取所有正文。网页端 Worker 应按以下状态推进：

```text
build_index
→ graph
→ concept_tracking
→ module_extract
→ integrated_notes
→ provisions
→ distinctions
→ case_drills
```

对应输出：

- `知识图谱.md`：宏观坐标系。
- `概念追踪表.md`：跨课次概念演进。
- `整合版笔记.md`：去重、重组后的体系笔记。
- `法条精读表.md`：核心法条与要件拆解。
- `辨析表.md`：易混概念对比。
- `案例练习库.md`：事实题与考查方向。

网页端应显示每一步的状态、产物和错误信息。失败时只回退当前步骤，不影响已经完成的上游产物。

## 网页端相对原 Skill 的改良点

- 材料包模型：原流程偏向文件目录，网页端显式支持一份 SRT + 多份 PPTX。
- 课程批处理：网页端显式支持多份 SRT 顺序运行，并用 rolling context 保持上下文连续。
- 用户确认产品化：preflight、大纲、材料包确认都在网页端保存状态。
- 状态可恢复：每个 job 的状态写入数据库，而不仅依赖本地 changelog。
- 权限一致：输出笔记默认私有，发布时进入内容快照权限模型。
- 渐进式产物可见：整合阶段每一步都可以在网页端查看和重跑。

## 后端 Worker 兼容方式

Worker 在运行前把数据库和 Storage 中的材料包还原为 Skill 需要的目录：

```text
课程目录/
├── raw/
│   ├── 课程名 - 日期第X-Y节 - 老师_原文.srt
│   ├── 课程名 - 日期第X-Y节 - 老师_PPT_01.pptx
│   └── 课程名 - 日期第X-Y节 - 老师_PPT_02.pptx
├── working/preferences.json
└── ...
```

然后调用现有 `workflow.py run --dir ./课程目录`。

网页端不需要复制 Skill 的全部逻辑；只需要维护状态、文件、偏好和确认点。
