# AI 协作改动的一键交付流程

更新时间：2026-06-28

## 一、目的

多文件改动不再要求用户逐条复制终端命令。除纯文案讨论或单行修改外，后续代码交付默认提供一个自包含补丁目录，其中至少包括：

```text
apply-*.py
apply-test-push.sh
README.md
files/
```

用户解压后只执行 `apply-test-push.sh`。脚本负责应用改动、验证、提交和推送开发分支。

## 二、脚本必须做到

1. 只允许在 `codex/homepage-phase1` 上运行，绝不修改、合并或推送 `main`；
2. 在开始前获取远端状态，远端领先时安全停止，避免覆盖他人改动；
3. 清理 `test-results/junit.xml` 等已知生成文件；
4. 允许上一次失败留下的“本补丁已知文件”继续存在，从半应用状态恢复；
5. 若发现不属于本补丁的本地改动，列出文件并停止，不擅自暂存或覆盖；
6. 补丁应用必须幂等，重复运行不得重复插入代码或文档；
7. 依次运行 `git diff --check`、针对性 Jest、`npm run build`；
8. 任一检查失败立即停止，不 commit、不 push；
9. 只精确暂存本轮文件，禁止 `git add .`；
10. 禁止使用 `--no-verify` 绕过仓库门禁；
11. 全部通过后自动 commit 并 push `codex/homepage-phase1`；
12. 不读取、打印、复制或提交 `.env*`、访问令牌和密钥。

## 三、失败后的处理

测试或构建失败后，工作区可能保留本轮补丁文件，这是正常现象。下一份修复包必须：

- 识别这些已知文件；
- 在其基础上继续修复；
- 不要求用户回滚或手动逐文件处理；
- 重新跑完整门禁后再提交。

用户只需提供失败日志。修复包仍保持“一条命令执行”的交付方式。

## 四、文档更新

涉及架构、数据模型、权限、部署、交付方式或重要产品约束的改动，脚本应同步更新：

```text
AGENTS.md
NEXT_ASSISTANT_BRIEF.md
PROJECT_STATUS.md
docs/LAW_TECH_PROGRESS.md
```

根据主题再更新相应专项文档。文档更新同样必须幂等。

## 五、边界

一键脚本只能自动提交它明确列入白名单的文件。用户自己的未提交工作、未知生成物和敏感配置都不属于自动处理范围。生产分支与生产环境仍需单独、明确授权。
